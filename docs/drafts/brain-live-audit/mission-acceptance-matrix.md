# What would substantiate autonomous delivery

This is an evaluation plan, not a completed run. Its subject is the installed
Brain/harness combination and an actual supported worker adapter. Generating a
fixture app by hand while bypassing Brain would not test this claim.

| Boundary | Required observation | Deliberate failure / control |
|---|---|---|
| Idea intake | Mission records user intent, outcome, exclusions, existing authority and target | Vague optional choice uses a reversible default; consequential missing authority blocks only dependent work |
| Planning | Accepted tasks cover the outcome, all prerequisite sprints and real project conventions | Earlier unfinished task, missing dependency and cycle remain visible; independent ready task still executes |
| Dispatch | Native transport returns worker identity, owned checkout and attempt; worker start is read back | Lost response reconciles actual start; duplicate request cannot create competing owners |
| Build | Worker changes only mission-owned paths and executes real entrypoint checks | Concurrent peer edit stays untouched; a compiler failure cannot turn into a success-shaped summary |
| Review | Independent reviewer checks the frozen candidate against acceptance evidence | Self-authored passing assertions do not suppress an independently reproduced failure |
| Persistence | New data survives process restart and caller reload with intended identities | Cross-user denial, empty/error states, duplicate requests and retry after uncertainty |
| Release preparation | Prior live artifact is frozen before effect; full tested candidate and target are bound | Candidate changes, stale ledger, removed required row and wrong target must refuse promotion |
| Live verification | Actual deployed version, browser interaction and resulting persisted state match | A cached page, login shell, unrelated successful health request or screenshot from old code cannot pass |
| Recovery | Crash state reconstructs owner, attempt, external effects and outstanding acceptance | Kill before dispatch response, after write, during verification and before acknowledgement |
| Reporting | Result persists before notification; supervisor acknowledges acceptance separately | First-turn completion, no later Stop, cooldown and duplicated delivery still converge |
| Termination | Completion occurs at the requested boundary with no required check missing | Exhausted retries remain failed/blocked with next action; scores, timestamps and empty scans cannot complete the mission |

Use disposable repositories and synthetic accounts/data. Start with an owned
local target and then an explicitly authorized preview platform. Establish the
required browser/worker capabilities before creating an external fixture.
Record actual model, tool versions, candidate, input population, commands,
observed outcomes, interventions, elapsed time and cost. Compare a frozen
baseline, the proposal and one viable alternative on the same missions.

Advance end-to-end mission-performance ratings only after repeated independent
missions, including failed attempts and recovery outcomes. Local source/control
maturity is a separate assessment and may change after bounded fixture or
procedure evidence; it does not establish improved installed-runtime performance. A single successful run is evidence for that
run, not an arbitrary-task success probability.
