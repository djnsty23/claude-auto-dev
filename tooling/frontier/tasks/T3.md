## check-queue-freshness reports a verdict when git failed

A full gate on a loaded machine saw `plugins/autodev-core/scripts/check-queue-freshness.js`
read a premise that still holds as STALE. The cause was never captured: the
script keeps nothing of what git said when a call fails. Reproducing it, I
found other ways a broken git call becomes a verdict:

- A `git grep` that itself fails (`grep.threads=-1` via `GIT_CONFIG_*`) turns
  an expect=present premise STALE, and the run exits 3.
- With one loose blob deleted, a file= premise on that file reads MISSING-FILE,
  and whole-tree premises read STALE (expect=present) or FRESH (expect=absent).
- With git missing from PATH, every premise just says "could not resolve origin/HEAD".

Correct behaviour: a git call that did not run cleanly is not an answer. Its
premise is UNCHECKABLE, never STALE, MISSING-FILE or FRESH, and counts like a
premise-less item: toward exit 2 when nothing else was checked, never exit 3.
Premises git answered cleanly in the same run keep their verdicts.

## Interface the checks use

- `--json`: such a result carries `gitFailure`, an object with at least `status`
  (git's exit status) and `stderr` (git's stderr), and `population.gitFailed`
  counts those results.
- Its `why` names the subcommand, how it ended and git's first stderr line, as
  in `git grep exited 128: <stderr line>`. A spawn failure names its error code (`ENOENT`).
- The human report prints `git itself failed on N premise(s)`, and gives the
  "carried nothing checkable" advice only for items that have no premise.
