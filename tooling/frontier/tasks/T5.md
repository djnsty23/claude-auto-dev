## check-branch-landed calls additive PRs BEHIND once the trunk moves on

`plugins/autodev-core/scripts/check-branch-landed.js` read all 10 open PRs of a
Next.js product repo as BEHIND, "landing it is a revert", for example
`+15440 / -42957`. Each PR only adds work (mostly new route files such as
`app/[id]/page.tsx`) and merges clean. BEHIND feeds branch deletion and PR
closing, so this verdict can close unlanded work. It shows up once the trunk
has moved on after the branch forked.

Correct behaviour: work the trunk gained after the fork is not the branch's to
revert. An additive branch behind a moving trunk is UNLANDED, and its reason
counts only lines its own commits add and delete. BEHIND means the branch's own
commits mostly delete, and its reason should say it may be a deliberate removal
to read before closing. A branch whose files are byte-identical on the trunk is
still LANDED-CONTENT. A branch with no merge base with the trunk is UNKNOWN.

Also name paths the branch touched that the trunk changed too since the fork,
to something other than the branch's version: a conflict risk, not a revert.
It never changes a verdict, and a file the trunk never had is not one.

## Interface the checks use

- The exported `classify(evidence)` reads, on each `evidence.files` entry, a
  `baseBlob` beside `trunkBlob` and `branchBlob`: the path's blob at the merge
  base, null when absent there. A missing `baseBlob` means not measured, and
  such a path is never named.
- The reason keeps its `+A / -D` counts. With conflict paths it says
  `conflict risk`, then the paths, with a count `N path(s)`, listing at most
  five and ending `(+K more)` for the rest. Without any, the word `conflict`
  does not appear in the reason.
