## Release tags ship lightweight and the lag check reads them as fine

`tooling/bump.js` and `tooling/bump.sh` end by printing the manual release
steps, and their tag step is `git tag v<version>`. Two releases shipped with
lightweight tags made that way. A lightweight tag records no tagger and no
date, which is what an audit of a release reads.

`tooling/check-release-lag.js` checks that the tag `v<VERSION>` exists locally
or on the remote, and today it is green for a lightweight tag.

Correct behaviour:

- Both bump scripts print an annotated tag step:
  `git tag -a v<version> -m "v<version>"`.
- When the release tag is present locally, the check reads its object type.
  A lightweight tag makes the verdict RED, with the reason
  `tag v<version> is lightweight: re-cut it with git tag -a`.
- The human-readable tag line ends with `, annotated` or `, LIGHTWEIGHT` when
  the local tag was read, and is unchanged when there is no local tag.
- `--json` output carries `tag.annotated` as `true` or `false` when the local
  tag was read.
- A failure to read the tag's type is reported as an error, not as either
  verdict.

An annotated tag, a missing tag and an unreadable remote keep the verdicts
they have today.
