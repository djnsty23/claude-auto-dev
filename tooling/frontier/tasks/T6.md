## The cost window counts sync rows instead of tasks

`tooling/window-specs.js` defines the `cost-window` spec, which reads
`autodev/delivery/outcomes.jsonl` and reports days whose accepted tasks carry
no cost. The spec reads every row in that file as one task finished at `at`.

The file's real writer, `delivery-outcomes.js sync`, works differently:

- it appends a row with `type: 'attempt'` for each attempt (attempt rows carry
  no cost by design) and a row with `type: 'outcome'` for each task;
- it appends again whenever a task's outcome changes, so one task can have
  several outcome rows, and the newest one is the truth;
- it stamps `at` with the sync time, often the next day. The day the task was
  worked is its `lastAttemptAt`.

So attempt rows count as violations, a re-synced task counts twice, and tasks
land on the day the observer ran.

Correct behaviour:

- Each task (`taskId`) is graded once, on its newest outcome row by `at`, and
  is dated by that row's `lastAttemptAt`. Attempt rows and rows without a
  usable date are ignored.
- The accepted-cost total counts only accepted tasks with a finite `costUsd`
  whose `lastAttemptAt` falls on a window day on or after the spec's
  admissible date. A task last attempted before the window does not meet it.
- The admissible date becomes `2026-10-25`, the first day the sync observer
  wrote complete rows, and the source text names the outcome rows of
  `delivery-outcomes.js sync`.

The other window specs are unchanged.
